# ADR-0005: docs/knowledge/ content stays untracked by design; add per-file categories, defer a second collection

**Status:** Accepted
**Related code:** `services/api/app/services/knowledge/loader.py`
**Related tests:** `services/api/tests/test_knowledge_loader.py`
**Related docs:** `docs/knowledge/` (the corpus itself), `adr-0004-knowledge-rag-qdrant-cloud.md`,
`.gitignore` (`docs/knowledge/**` with `README.md`/`.gitkeep` exceptions)

## Context

`adr-0004` shipped the ingestion pipeline (loader/embeddings/qdrant_store/ingest) and
`docs/knowledge/README.md`, but the thirteen content files that README's own table
points at (`topology.md`, `network.md`, `service-catalog.md`, `service-detail/*.md`,
`resource-mgmt.md`, `security-access.md`, `admin-runbook.md`, `flow-processes.md`,
`glossary.md`) are not in this repo. That's not an oversight: `.gitignore` explicitly
excludes `docs/knowledge/**` except `README.md` and `.gitkeep`, and both
`infra/docker-compose.yml` and `infra/docker-compose.prod.yml` bind-mount
`../docs/knowledge:/app/docs/knowledge:ro` from the host rather than `COPY`-ing it
into the image at build time. This matches the classification on the README itself
("Internal document — Restricted use") -- the actual RIF SAS infra content is meant
to live on the deploy host / wherever docker-compose runs, populated out-of-band, not
in the public git history of this repo.

**Consequence for this patch: it does not add those thirteen files to git, and no
future patch touching this repo should either.** Populating them is an operational
step (copy the files into `docs/knowledge/` on the host, then
`POST /api/v1/knowledge/ingest`), not a code change. Running `/api/v1/knowledge/ingest`
against a checkout where that directory is genuinely empty (as any fresh `git clone`
of this repo will be) only embeds README.md -- a handful of chunks describing the
corpus, none of the actual infra knowledge -- until that operational step happens.
If the chat feels like it "knows nothing," check `GET /api/v1/knowledge/status`
(`points_count`) before assuming the code is broken.

## Decision

**Give every top-level file its own `category` instead of lumping them into
"general".** Before this change, `loader.py` only distinguished `service-detail`
(the five per-service files) from `general` (everything else -- topology, network,
security, runbooks, glossary, all mixed together). `/api/v1/knowledge/search` and
`qdrant_store.search()` already accept a `category` filter, but it could only ever
mean "service docs vs. everything else." A question scoped to security posture
(`security-access.md` + `admin-runbook.md`) or to network topology (`network.md`)
had no way to exclude the glossary or the resource-management doc from the
candidate set. `_TOP_LEVEL_CATEGORIES` in `loader.py` now maps each known filename to
its own category (`topology`, `network`, `service-catalog`, `resource-mgmt`,
`security-access`, `admin-runbook`, `flow-processes`, `glossary`, `overview` for
README.md); an unrecognized top-level file still falls back to `general`, so adding a
new doc later never breaks ingestion, it just isn't finely categorized until someone
adds it to the map.

**No second Qdrant collection yet, despite that being a natural question.** The
project roadmap (`documentation-projet-cortex.md`, Phase 8) calls for
auto-generated incident post-mortems to be "reinjected into the knowledge base."
That data has a genuinely different lifecycle from this corpus -- append-only,
timestamped, generated by the Anomaly/Remediation agents rather than hand-edited,
one entry per incident rather than one entry per doc revision -- which is a real
argument for its own `cortex-incidents` collection (or at minimum its own
`source_type` discriminator) rather than mixing it into `cortex-knowledge`, where a
flood of short incident summaries could crowd out the static reference docs in
similarity search. But no incident/post-mortem entity exists in the codebase yet
(Phase 2's anomaly/RCA output isn't persisted as a queryable incident record), so
there is nothing to embed. Standing up a collection for data that doesn't exist yet
would be schema guessing. **When Phase 8 lands an actual incident/post-mortem model,
revisit this ADR** and decide then between a second collection vs. a `source_type`
payload field on the existing one, informed by the real shape of that data instead of
a hypothetical one.

**`docs/architecture/*.md` (this file included) stays out of the RAG corpus.** Those
are implementation notes about how Cortex itself is built (Neo4j graph schema,
internal endpoint contracts). They answer "how does Cortex's topology sync work,"
not "how does our OpenStack cloud work" -- a different audience and a different
failure mode if mixed in (an operator asking about Cinder latency shouldn't get a
chunk about `graph_db.py`'s read helpers back). If a future cockpit-onboarding
feature specifically wants Cortex-self-knowledge search, that's a separate,
explicitly-scoped collection, not an expansion of `cortex-knowledge`.

## Consequences

- Once the 13 content files are actually present under `docs/knowledge/` on the host
  (an operational step, not this patch), `/api/v1/knowledge/ingest` embeds 76 chunks
  across 14 files instead of just README.md's 6 -- verified locally against the real
  corpus content while writing this ADR.
- Existing callers that pass `category="general"` will get a smaller result set than
  before (the eight top-level files that used to share that bucket now have their own
  categories) -- there were no such callers yet outside tests, which this patch
  updates.
- `_TOP_LEVEL_CATEGORIES` is the single place to register a category for a new
  top-level file; forgetting to do so degrades gracefully to `general` rather than
  erroring.
